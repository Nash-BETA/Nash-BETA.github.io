# 15章：アーキテクチャとは？ まとめ

## 要点

### アーキテクトとは何者か

- アーキテクトは最上位のプログラマーであり、自分でもコードを書き続ける必要がある
- コードから離れると、現場のプログラマーが何に困っているかが見えなくなる
- 「システムが何をするか」ではなく「システムがどう作られ、どう保たれるか」を決めるのが仕事

### 開発

- アーキテクチャは、その開発チームが開発しやすくなるような形にすべき
- 少人数なら形式張った設計はむしろ邪魔。大人数ならコンポーネント分割が必要
- 「正しいアーキテクチャ」はチームサイズに依存する＝銀の弾丸はない

### デプロイ

- 単一のアクションでデプロイできる状態を目指す
- 開発初期からデプロイを意識しないと、後から構造を作り直す羽目になる
- マイクロサービスの各設定や接続、起動のタイミングでエラーの原因になることもある

### 運用

**インフラ運用の話**

- 運用コストはハードウェアを追加すれば解決することが多い（サーバー足す、スペック上げる）
- 開発・デプロイ・保守に比べるとアーキテクチャ上の優先度は低い

**コード運用の話**

- アーキテクチャが優れていれば、システムの運用方法を開発者が見ればすぐわかる
- ディレクトリ構造やコードの組み方で「何をするシステムか・どこに副作用があるか」が読み取れることが理想

### 保守

- ソフトウェアシステムのすべてにおいて保守は最もコストがかかる
- **洞窟探索**：新しい機能や不具合の修正においての最適な場所や戦略を見つけるコスト
- **リスク**：変更を行っているうちに意図しない欠陥を生み出す可能性が生まれるコスト
- 良いアーキテクチャはこの2つを小さくするためにある

### 選択肢を残しておく

- ソフトウェアは2種類の価値を持つ：**振る舞い**（機能）と**構造**（変更に対する柔軟性）
- 方針（ビジネスルール）と詳細（DB・Web・FW）を分け、詳細の決定をできるだけ遅らせる
- 遅らせた分だけ情報が集まり、良い判断ができる

### デバイス依存性

- 昔のプログラムはデバイスに依存していた（このプリンタに出す、このカードリーダーから読む、のようにデバイスを直接指定）
- デバイスが変わるとプログラムも全書き直し
- OSがデバイスを抽象化（標準入出力など）し、プログラムはデバイスを意識しなくてよくなった

### ダイレクトメール

- 「磁気テープに印刷データを書き出す → 別プロセスがプリンタに流す」という古い構成
- アプリ側が「磁気テープに書く」と決め打ちしていたため、媒体を変えると全書き直し
- 方針（印刷したい）と詳細（どこに書くか）が密結合していた典型例

### 物理アドレス指定

- 昔はデータを保存するとき、ディスク上の物理アドレス（シリンダ・トラック・セクタ）をコードに直接書いていた
- ディスクを替えるとアプリ全書き直し
- OSがファイルシステムを提供したことで、アプリは「ファイル名」で扱えるようになった

### 結論

- アーキテクチャの本質は「形（shape）」を作ること
- システムが「何をするか」ではなく、「どう作られ、どう保たれ、どう変えられるか」を決める
- 詳細の決定をできるだけ遅らせて選択肢を残す。これが変更可能性を生み、ソフトウェアを「ソフト」たらしめる

## 疑問①：「アーキテクチャが優れていれば運用方法がすぐわかる」って具体的にどういうこと？

ディレクトリ構造やコードの組み方で、「このシステムは何をするのか・どこに副作用があるか」が読み取れる状態のこと。

例えばRailsで以下のような構造だと「Railsアプリだな」としかわからない。

```
app/
├── controllers/
├── models/
└── services/   # 雑に全部ここ
```

これに対して、ドメインとユースケースが構造に表れていれば、ディレクトリを開いた瞬間に「これはECの注文・請求システムで、日次締めバッチがあって、Stripeを使ってる」が読み取れる。

```
app/
├── orders/                   # 注文ドメイン
│   ├── use_cases/
│   │   ├── place_order.rb
│   │   ├── cancel_order.rb
│   │   └── issue_refund.rb
│   ├── entities/
│   └── jobs/
├── billing/                  # 請求ドメイン
│   ├── use_cases/
│   │   └── charge_card.rb
│   └── gateways/
│       └── stripe_gateway.rb # 外部依存が明示されてる
└── batches/
    └── daily_settlement.rb
```

なお、Martinの「運用」節は**インフラ運用（ハードで殴れる）**と**コード運用（可視性）**の2つが混ざっているため混乱しやすい。本文上は別物として分けて読むと整理しやすい。

## 疑問②：「洞窟探索」って仕様調査のこと？

近いが、微妙にズレる。

- **仕様調査**：「この機能は**何をしている**か」を理解する作業（ドキュメント・PdMに聞く・過去チケットを見る）
- **洞窟探索**：「**どこを触ればいいか・触ったら何が壊れるか**」を見つける作業（grep・依存を追う・callsiteを探す・関連テストを読む）

「注文キャンセル時にバグがある」という案件が来たときの対比：

- 仕様調査：キャンセル時に返金は自動で走る仕様だっけ？ メール通知はどこまで？
- 洞窟探索：`OrderCancellation` の処理はどのクラスに散らばってる？ `refund` を呼んでるのは何箇所？ ここ直すとどのテストが落ちる？

実務では両方混ざって進めるが、Martinが「保守コストがかかる」と言っているのは後者（洞窟探索）のほう。仕様はPdMに聞けば答えが返ってくるが、**コードの地形は自分で掘るしかない**から時間とリスクが膨らむ。

## 疑問③：「特定のデバイスに直接書いていた」って、デバイス依存だったってことかな？

その通り。コードイメージで対比すると：

```ruby
# デバイス依存
printer = HPLaserJet4.new
printer.send_ascii(data)   # HPLaserJet4のAPIを直接叩いている
```

プリンタをCanonに替えた瞬間、このコードは全部書き直し。

```ruby
# デバイス独立（OSが抽象化してくれた後）
File.open("/dev/stdout", "w") { |f| f.puts data }
# 出力先がプリンタでもファイルでも画面でも、コードは同じ
```

「方針（データを出力する）」と「詳細（どのデバイスに）」を分離したことで、**詳細を差し替え可能になった**のが進化のポイント。

## 疑問④：3つの例（デバイス依存性・ダイレクトメール・物理アドレス指定）って結局どういうこと？

全部同じ話の繰り返し。**「アプリのコードに『どこに書くか・どのデバイスを使うか』を直接書いちゃうと、後で詰む」**という話。

| やってたこと | 結果 |
|------------|------|
| プリンタの型番をコードに書く | プリンタ替えたら全書き直し |
| 磁気テープに直接書き込む | 媒体替えたら全書き直し |
| ディスクのシリンダ番号をコードに書く | ディスク替えたら全書き直し |

これをOSが抽象化（標準入出力・ファイルシステム）してくれたおかげで、アプリは「ファイル名で読み書き」するだけで済むようになった。

Railsで言うと：

```ruby
# 物理アドレス指定的な書き方（やったらアウト）
Mysql2::Client.new(host: 'db-prod-01.internal', port: 3306).query("SELECT ...")

# 抽象化された書き方
User.where(active: true)
# ActiveRecordが「DBがどこにあるか・MySQLかPostgresか」を隠してくれてる
```

Martinが70年代の例で言いたいのは、**「現代のお前らはActiveRecordやFile APIのおかげで楽してるけど、昔の人はこの抽象化を一段ずつ積み上げてきたんだぞ。だから自分でコード書くときも『方針と詳細を分ける』を意識しろよ」**という話。
