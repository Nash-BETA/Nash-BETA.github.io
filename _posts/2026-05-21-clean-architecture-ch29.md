# 29章：クリーン組込みアーキテクチャ まとめ

## 要点

- 組込みソフトウェアもソフトウェアである。SOLID・依存ルール・境界の原則は組込みでも有効
- ハードウェア依存を放置すると、ソフトウェアは「ファームウェア」に堕落する
- HAL（Hardware Abstraction Layer）でハードを抽象化することで、ソフトウェアはハードから独立できる
- これにより、テスト可能性、変更可能性、開発の並列性が確保される

---

## 疑問①：「適性テスト」って何？ Web エンジニアにも関係ある？

Martin の問いかけ：「**そのコード、ハードウェアが変わったときに生き延びるか？**」

- 生き延びる → 適性あり（クリーンに作られている）
- 死ぬ → 適性なし（ソフトウェアではなくファームウェア）

組込み系のコードは、ハードウェアにべったり依存していることが多い。特定のチップのレジスタを直叩き、センサーの仕様変更で大規模書き換え、ハードが変わる = ソフトウェア丸ごと作り直し。Martin から見るとこれは「ソフトウェアじゃなくてファームウェア」。

### Web エンジニアへの翻訳

組込みのハードウェア依存 = Web の DB / フレームワーク依存、と読み替えるとピンと来る。

- 「Postgres が変わったら全コード書き換え」=「ハードが変わったら全ファーム書き換え」
- 「Rails 8 に上げたら何百ファイル修正」=「新チップに対応するため大改修」

組込みでこれが起きやすいのは「ハードとソフトの距離が近い」から。でも本質的には Web の世界で起きている問題と同じ。

## 疑問②：ターゲットハードウェアのボトルネックを解決する HAL とは？

ハードウェア依存が開発のボトルネックになる：

- 実機がないとテストできない（開発者全員に実機配布が必要）
- ハードが変わると全部書き換え
- ハード開発とソフト開発の並列化ができない

Martin の処方箋：**レイヤー分離**。

```
Software（アプリのロジック）
   ↓
HAL（Hardware Abstraction Layer：ハードウェア抽象化層）
   ↓
Firmware（ハード固有のコード）
   ↓
Hardware（実機）
```

- Software は HAL にしか依存しない
- HAL は「ハードに何を頼むか」の抽象インターフェース
- Firmware は HAL を実装する具象。ハード依存はここに閉じ込める

メリット：

- Software は HAL のモックでテストできる（実機不要）
- ハードが変わっても、Firmware だけ作り直せばよい
- ハード開発が完了する前に Software 開発を始められる

### Web への翻訳：リポジトリパターン

このパターンは Rails でも頻出。

```
ビジネスロジック（UseCase）
   ↓
リポジトリ抽象（OrderRepository）
   ↓
ActiveRecord 実装（具象）
   ↓
PostgreSQL
```

- UseCase は `OrderRepository` という抽象にしか依存しない
- 実装が ActiveRecord か Sequel か Memory ストアかは関心外
- テストでは Memory ストアに差し替えて高速化

組込みの HAL = Web のリポジトリパターン、と読み替えると同じ構造。

## まとめ

組込みでも Web でも、「**詳細を抽象の裏に隠す**」のが本質。ハード／DB／フレームワーク、何であれ「変化しうる詳細」は同じように扱える。「組込みだから」「Web だから」と分けて考えるのは、原則の捉え方として狭い。
