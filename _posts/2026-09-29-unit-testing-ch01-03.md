# 第1部（1〜3章）まとめ

## 第1章 なぜ、単体（unit）テストを行うのか？

### 要点

- 議論は「単体テストを書くべきか？」から「良い単体テストとは何か？」に移っている
- 単体テストの目的は「**プロジェクトの成長を持続可能にすること**」。設計が良くなるのは副産物
- テストの書きやすさで判定できるのは悪い設計だけ（書きづらい → 設計が悪い、は言える。書きやすい → 設計が良い、は言えない）
- 質の悪いテストは失速を遅らせるだけで、最終的にはテストが無いのと同じ結果になる
- テストコードも「資産ではなく負債」。価値が保守コストを上回るテストだけを残す
- 網羅率（coverage）は「質が悪い」ことは示せるが、「質が良い」ことは示せない
- 良いテスト・スイートの特徴
  - テストすることが開発サイクルの中に組み込まれている
  - コードベースの特に重要な部分（ドメイン・モデル）のみがテスト対象となっている
  - 最小限の保守コストで最大限の価値を生み出すようになっている

---

### 疑問①：単体テストの目的は「プロジェクトの成長を持続可能にすること」、すごく大事では？

その通りで、本全体がこの目的に対して「どんなテストが役に立つか」を測っていく構成になっている。

- テストが無いと、変更のたびに無秩序（ソフトウェア・エントロピー）が増えて開発速度が落ちていく
- テストがあっても質が悪いと、失速を遅らせるだけ
- なので「テストの数」ではなく、「成長を持続させるのに役立つか」でテストを評価する

### 疑問②：網羅率も完璧じゃないんだね

完璧ではない。目安にはなるが、目標にすると害になる。

網羅率は2種類あり、どちらにも弱点がある。

```ruby
# if で書いた場合：`true` の行は実行されないので、コード網羅率 80%（4行/5行）
def long_string?(input)
  if input.length > 5
    true
  else
    false
  end
end

# 三項演算子に書き換えた場合：全行実行されるので、コード網羅率 100%
def long_string?(input)
  input.length > 5 ? true : false
end

RSpec.describe "long_string?" do
  it { expect(long_string?("abc")).to be false }
end
```

- **コード網羅率（行網羅率）**：コードをコンパクトに書くだけで上がる。検証している内容は変わらない
- **分岐網羅率**：書き方に左右されない（上の2つはどちらも50%。SimpleCov では `enable_coverage :branch`）

ただし分岐網羅率でも次の2点は測れない。

- **検証したかどうか**：`expect` を書かずに実行するだけのテストでも100%になる
- **ライブラリの中の分岐**：`Integer("5")` の中にある `nil` や空文字などの分岐は計測の対象外

網羅率を目標にすると、何も確認しないテストが量産される（著者の実体験では、100%を強制した結果ルールごと撤廃された）。本の例えは体温計で、熱を測るのは正しいが、体温を目標値にすると患者に冷風を当て始める。

### 疑問③：1章は課題感を提示しただけ？

そう。1章は課題の提示と本全体の地図で、解決策（テストを評価する枠組み）は第4章から出てくる。

「重要な部分に労力を集中する」の対象として、本はドメイン・モデルとそれ以外を分けている。

| 本の分類 | Rails で言うと |
| --- | --- |
| ドメイン・モデル（重点的にテストする） | 料金計算・ポイント付与・状態遷移などの業務ルール。モデルのメソッドや PORO |
| インフラに関するコード | ジョブの基盤処理、ファイルの入出力 |
| 外部サービスや依存関係にあるもの | DB、外部 API クライアント |
| 構成要素同士を結び付けるコード | コントローラ、サービスクラスの呼び出し順を並べるだけの部分 |

Rails は ActiveRecord でドメインと DB が同居しているので、この切り離しがそもそも難しい。ここは第2部で改めて扱う。

## 第2章 単体テストとは何か？

### 要点

- 単体テストの3つの性質：①「単体」と呼ばれる少量のコードを検証する ②実行時間が短い ③隔離された状態で実行される
- ③の「何を隔離するか」の解釈で2つの学派に分かれた
  - **ロンドン学派**：テスト対象のクラスを協力者オブジェクトから隔離する。単体 = 1つのクラス
  - **古典学派**：テスト・ケース同士を隔離する。単体 = 1単位の振る舞い
- 著者（と本書）は古典学派を採用。ロンドン学派はテストが実装の詳細に結び付き、壊れやすくなるため
- 本書の単体テストの定義：①1単位の振る舞いを検証する ②実行時間が短い ③他のテスト・ケースから隔離された状態で実行される。1つでも欠けたら統合テスト
- E2E テストは統合テストの一種で、プロセス外依存をすべて（またはほぼすべて）本物で扱う

---

### 疑問①：ロンドン学派はモックを使う、という話？

ざっくりその理解で合っている。違いは**どこまでテスト・ダブルにするか**。どちらの学派もテスト・ダブル自体は使う。

- **ロンドン学派**：テスト対象が使っている他のクラスは、基本すべてテスト・ダブルにする
- **古典学派**：他のクラスも本物を使う。テスト・ダブルにするのは DB などテスト同士で共有されるものだけ

`Customer` のテストで、`Store` を本物にするか、テスト・ダブルにするかに絞るとこうなる。

| | `Store`（在庫を持つクラス） | 最後に確認すること |
| --- | --- | --- |
| 古典学派 | 本物を使う | 在庫が 10 → 5 に減ったか（**結果**） |
| ロンドン学派 | テスト・ダブルにする | `Customer` が「在庫を減らして」と `Store` に頼んだか（**やり取り**） |

```ruby
# 古典学派：Store は本物を使い、最後に Store の「状態」を確認する
it "在庫が十分にある場合、購入は成功する" do
  store = Store.new
  store.add_inventory(:shampoo, 10)
  customer = Customer.new

  success = customer.purchase(store, :shampoo, 5)

  expect(success).to be true
  expect(store.inventory(:shampoo)).to eq 5
end
```

```ruby
# ロンドン学派：Store をテスト・ダブルに置き換え、Store との「やり取り」を確認する
it "在庫が十分にある場合、購入は成功する" do
  store = instance_double(Store, enough_inventory?: true, remove_inventory: nil)
  customer = Customer.new

  success = customer.purchase(store, :shampoo, 5)

  expect(success).to be true
  expect(store).to have_received(:remove_inventory).with(:shampoo, 5).once
end
```

線引きの違いは、何を「単体」と考えているかから来る。ロンドン学派は1クラスだけを切り出してテストしたい。古典学派は「購入すると在庫が減る」という振る舞いが2クラスにまたがるなら、両方を本物で動かして確かめればよいと考える。

C# ではモックを作るのに `IStore` インターフェイスが必要だったが、Ruby では `instance_double(Store, ...)` で具象クラスから直接作れる。本の第11章では具象クラスのテスト・ダブルはアンチ・パターンとされるが、`instance_double` はクラスに無いメソッドを指定するとエラーにするので事情が少し違う（第11章で改めて扱う）。

### 疑問②：モックで合っている？スタブじゃなくて？

正確には、ロンドン学派が置き換えるのは**テスト・ダブル**で、モックとスタブはその中の種類。2章の本文はこの区別をせず「モック」と書いている（詳細は第5章）。

| | 役割 | 上の例では |
| --- | --- | --- |
| **スタブ** | テスト対象に**入力を渡す**（決まった答えを返す） | `enough_inventory?: true`（「在庫あります」と答えるだけ） |
| **モック** | テスト対象から**出ていく呼び出しを確認する** | `have_received(:remove_inventory)`（「在庫を減らして」と頼んだかを確認） |

上の `store` はスタブとモックの両方の役を兼ねている（本の 5.1.4「モックとスタブの両方の性質を持ったテスト・ダブル」）。

```ruby
store = instance_double(Store, enough_inventory?: true, remove_inventory: nil)  # ← スタブとして答えを返す

customer.purchase(store, :shampoo, 5)

expect(store).to have_received(:remove_inventory).with(:shampoo, 5)             # ← モックとして呼び出しを確認
```

RSpec の `double` / `instance_double` はテスト・ダブル全般を作るメソッド。スタブとして使うかモックとして使うかは、`allow`（答えを返させる）と `expect(...).to have_received`（呼ばれたか確認する）のどちらで使うかで決まる。

### 疑問③：どの依存をテスト・ダブルにするのか？

依存を3種類に分けると線引きがはっきりする。

```
依存
├─ 共有依存（テスト・ケース同士で共有されるもの）
└─ プライベート依存（共有されないもの）
    ├─ 可変依存（状態が変わるもの）
    └─ 不変依存 = 値オブジェクト（状態が変わらないもの）
```

| 分類 | 本の例 | Rails で言うと | 古典学派 | ロンドン学派 |
| --- | --- | --- | --- | --- |
| 共有依存 | DB、ファイル・システム、static な可変フィールド | DB、Redis、`Rails.cache`、クラス変数 | テスト・ダブルにする | テスト・ダブルにする |
| 可変依存 | `Store` | 状態を持つモデルのインスタンスや PORO | **本物を使う** | **テスト・ダブルにする** |
| 不変依存（値オブジェクト） | `Product.Shampoo`、`5` | Symbol、Integer、`Date`、freeze した値オブジェクト | 本物を使う | 本物を使う |

**両学派の違いは「可変依存」の行だけ。** ロンドン学派がテスト・ダブルにする「共有依存」と「可変依存」をまとめて協力者オブジェクト（collaborator）と呼ぶ。

なお「共有依存」と「プロセス外依存」は似ているが別物。読み込み専用の API はプロセス外依存だが共有依存ではなく、クラス変数やシングルトンはプロセス内だがテスト同士で共有すれば共有依存になる。本書は区別が必要な場面以外は同じ意味で使う。

### 疑問④：「振る舞い」のテストと「コード」のテストは、どっちがどっち？

```ruby
# 1単位の振る舞い（古典学派）：非開発者にも伝わる
it "注文を確定すると、在庫が減り、確認メールが送られる"

# 1単位のコード（ロンドン学派）：クラスの中身の説明になっている
it "OrderService が InventoryService#decrement を呼ぶ"
it "OrderService が OrderMailer.confirmation を呼ぶ"
```

中身まで書くとこうなる。

```ruby
# 古典学派：InventoryService は本物を使い、「結果」を確認する
it "注文を確定すると、在庫が減り、確認メールが送られる" do
  product = create(:product, stock: 10)

  OrderService.new.confirm(product, quantity: 3)

  expect(product.reload.stock).to eq 7                  # 在庫が減った
  expect(ActionMailer::Base.deliveries.size).to eq 1    # メールが送られた
end
```

```ruby
# ロンドン学派：協力者をテスト・ダブルにして、「やり取り」を1つずつ確認する
it "OrderService が InventoryService#decrement を呼ぶ" do
  inventory = instance_double(InventoryService, decrement: nil)
  allow(InventoryService).to receive(:new).and_return(inventory)

  OrderService.new.confirm(product, quantity: 3)

  expect(inventory).to have_received(:decrement).with(product, 3)
end
```

下のテストは、`InventoryService#decrement` を `Product#decrease_stock!` に移すと、在庫が正しく減っていても落ちる。上のテストは結果しか見ていないので落ちない。これが「ロンドン学派のテストは実装の詳細に縛られる」ということ。

本の例えでは、「名前を呼ぶと犬が寄ってくる」が振る舞いのテストで、「名前を呼ぶと左前足を動かし、右前足を動かし、頭をこちらに向け…」がコードのテスト。

ロンドン学派の3つの長所への著者の反論も整理しておく。

| ロンドン学派の長所 | 著者の反論 |
| --- | --- |
| 細かな粒度で検証できる（1テスト＝1クラス） | 検証すべきは1単位のコードではなく1単位の振る舞い |
| 依存関係が複雑でも簡単にテストできる | 考えるべきは「複雑な依存をどうテストするか」ではなく「複雑な依存を作らないこと」。テスト・ダブルで隠しても設計の問題は残る |
| テストが落ちたとき原因の場所がすぐ分かる | 変更のたびにテストを回していれば、直前に触った箇所が原因だとすぐ分かる |

### 疑問⑤：学派は実装の設計思想で分かれるのでは？

半分その通り。

- ロンドン学派の聖典『実践テスト駆動開発（GOOS）』は、オブジェクト同士がメッセージを送り合う設計が前提。クラスを細かく分ける設計だと、やり取りを確認するテストが自然に合う
- 古典学派は、ドメイン・モデルに業務ルールを集めて内側から作る進め方と相性が良い
- 因果は逆向きにも働く。ロンドン学派の TDD で外側から進めると、設計がクラスを細かく分ける方向に寄っていく

ただし著者は好みの問題とは見ていない。どんな設計でも、やり取りを確認するテストはリファクタリングで壊れやすい。これを第4章で「リファクタリングへの耐性」として測る。

### 疑問⑥：振る舞いを大事にする層と、実行だけ担保する層とで、ハイブリッドにしてもいいのでは？

本の考え方とほぼ同じ。第7章でコードを4種類に分けていて、そのうち2つがこの話に当たる。

| 本の分類（第7章） | Rails で言うと | テストの方針 |
| --- | --- | --- |
| ドメイン・モデル、アルゴリズム（複雑だが依存が少ない） | 業務ルールを持つ model や PORO | **単体テストで振る舞いを細かく確かめる** |
| コントローラ（単純だが依存が多い） | Controller、処理の順番を並べるだけの Service | **統合テストで、通しで動くことを確かめる** |

違いが出るのは「実行を担保する層」のテストの仕方。

- **ロンドン学派的**：Service の単体テストで、内部のクラスをテスト・ダブルにして「呼んだか」を確認する
- **本の推奨**：Service の中の model や DB は本物のまま、統合テスト（request spec など）で通しで動かす。テスト・ダブルにするのはメールや外部 API だけ

テスト・ダブルにするかどうかの線は「層」ではなく「アプリの内側か外側か」で引く。

| Service が使う依存 | 本の結論 | 理由 |
| --- | --- | --- |
| `InventoryService` や model（アプリの内部） | 本物を使う | 内部のやり取りは実装の詳細。リファクタリングで変わってよい |
| メール送信、決済 API（アプリの外） | テスト・ダブルで**やり取りを確認する** | 外部とのやり取りは外から見える振る舞いそのもの |

第5章ではこれを「システム内コミュニケーション」と「システム間コミュニケーション」と呼んで区別する。疑問④の古典学派の例で `deliveries` を見ていたのも、メール送信というシステム間のやり取りを確認していたことになる（Rails のテスト環境では `delivery_method` が `:test` で、送る代わりに配列に溜まる）。

### 疑問⑦：ロンドン学派から見たら、全部統合テストに見える？

そう。同じテストでも、どの学派の定義で見るかで「単体」にも「統合」にもなる。

| 同じテスト | ロンドン学派から見ると | 古典学派から見ると |
| --- | --- | --- |
| `Customer` と本物の `Store` を使うテスト | 統合テスト | 単体テスト |
| model spec で `create` して DB に保存するテスト | 統合テスト | 統合テスト |

本書（古典学派）の定義を RSpec に当てはめるとこうなる。

| RSpec でよく書くもの | この本の定義では |
| --- | --- |
| model spec で `create(:order)` して DB に保存する | **統合テスト**（DB という共有依存に触っている） |
| model spec で `build` / `build_stubbed` だけで完結する | 単体テスト |
| PORO の spec | 単体テスト |
| request spec | 統合テスト |
| system spec（ブラウザを動かす） | E2E テストに近い |

Rails はテストごとにトランザクションを張ってロールバックするので、テスト同士の干渉はある程度防げている。それでも DB アクセスは遅いので「実行時間が短い」からは外れる。

統合テストと E2E テストの違いは、本物で扱うプロセス外依存の数。

| | 本物を使うプロセス外依存 | 本の例 |
| --- | --- | --- |
| 統合テスト | 1〜2個（自分で状態を作れる DB やファイル） | DB とファイルは本物、外部の決済サービスはテスト・ダブル |
| E2E テスト | すべて、またはほぼすべて | 決済サービスも含めて本物（用意できないものはテスト・ダブル） |

チームで「単体テストを増やそう」と話すときは、まずどちらの定義で話しているかを揃えないと噛み合わない。

## 第3章 単体テストの構造的解析

### 要点

- テストは準備（Arrange）・実行（Act）・確認（Assert）の3フェーズで書く（AAA パターン。Given-When-Then とほぼ同じ）
- 同じフェーズが複数ある、テストの中に `if` がある → 1つのテストで複数の振る舞いを検証しているサイン。テストを分ける
- 実行フェーズが2行以上になったら、テストではなくプロダクション・コードの設計（カプセル化）を疑う
- 確認は1つだけ、は誤り。1つの振る舞いが複数の結果を生むなら複数の `expect` は自然
- テスト対象は `sut`（RSpec なら `subject`）と名付け、依存と区別しやすくする
- 準備の共通化は `describe` 直下の `let` / `before` ではなく、引数で前提を指定できるファクトリ・メソッドで行う
- テスト名は厳格な命名規則（{テスト対象メソッド}_{事前条件}_{想定する結果}）に縛られず、非開発者にも伝わる事実として書く。テスト対象のメソッド名は入れない（ユーティリティは例外）
- パラメータ化テストはコード量と読みやすさのトレードオフ。基本は正常系と異常系を分ける
- RSpec の `expect(result).to eq 30` は、本が勧める読みやすい確認（Fluent Assertions）と最初から同じ形

テスト名は、本では次の順で良くしていく。

| 段階 | テスト名（日本語訳） |
| --- | --- |
| 厳格な命名規則 | `IsDeliveryValid_InvalidDate_ReturnsFalse` |
| 普通の言い回しにする | 不正な日付が指定された配達は、不正だと見なされるべきである |
| 「不正」を具体的にする | **過去の**日付が指定された配達は、不正だと見なされるべきである |
| 冗長な部分を削る | 過去の日付が指定された配達は、不正とすべきである |
| 「べき」をやめて事実にする | 過去の日付が指定された配達は、**不正である** |

RSpec の `describe '#メソッド名'` は、つなげて出力すると厳格な命名規則と同じ形になる点に注意。

```ruby
RSpec.describe DeliveryService do
  describe "#delivery_valid?" do
    context "when the date is invalid" do
      it "returns false" do
        # ...
      end
    end
  end
end
# => DeliveryService#delivery_valid? when the date is invalid returns false

# 本の指針に沿うと
RSpec.describe DeliveryService do
  it "過去の日付が指定された配達は不正である" do
    # ...
  end
end
```

### 疑問①：テストの中の if はやばいね。考えたこともなかった

`if` があると、そのテストが今どちらの経路を確かめているのかが読むたびに分からなくなる。分岐を持ち込んで良くなることは何も無いので、統合テストでも使わない。同じフェーズが複数あるのも同じサイン。

| 避けるもの | 理由 | 対処 |
| --- | --- | --- |
| 実行→確認→実行→確認と、同じフェーズが複数ある | 1つのテストで複数の振る舞いを検証している | テストを分ける。ただし遅い統合テストでは、まとめてもよい |
| テストの中の `if` | 複数のことを検証しているサイン。読みにくくなるだけで良いことが無い | テストを分ける。統合テストでも使わない |

「テストの形がおかしいときは設計を疑う」という点では、実行フェーズが2行になるのも同じ。

```ruby
# 実行フェーズが2行になっている
success = sut.purchase(store, :shampoo, 5)
store.remove_inventory(:shampoo, 5) if success
```

呼び出し側が2行目を忘れると、商品は渡したのに在庫が減らない（不変条件の侵害）。1回の呼び出しで両方が起きるよう `purchase` の中に閉じ込めるのがカプセル化。Rails だと「サービスを呼んだあと、呼び出し側で `save!` もしないといけない」形がこれに当たる。

### 疑問②：describe 直下の let や before はアンチ・パターン？ it ごとにメソッド化したものを使うのがいい？

本の主張はそう。正確には「同じコードを毎回書け」ではなく、**そのテストの結果に効く前提は、`it` の中を読めば分かるようにしておけ**という話。

```ruby
# 本がアンチ・パターンとする形
RSpec.describe Customer do
  let(:store) do
    Store.new.tap { |s| s.add_inventory(:shampoo, 10) }
  end
  subject(:sut) { Customer.new }

  it "在庫が十分にない場合、購入は失敗する" do
    expect(sut.purchase(store, :shampoo, 15)).to be false
    expect(store.inventory(:shampoo)).to eq 10   # ← 「10」がどこから来たのかは上を見ないと分からない
  end
end
```

| 欠点 | 上の例で言うと |
| --- | --- |
| テスト同士の結び付きが強くなる | `let(:store)` の在庫を 10 → 15 に変えると、別のテストが意図せず落ちる |
| テストが読みにくくなる | 各 `it` の中だけでは前提（在庫10）が分からず、上まで戻って読む必要がある |

```ruby
# 引数で前提を指定できるファクトリ・メソッドにする
RSpec.describe Customer do
  it "在庫が十分にある場合、購入は成功する" do
    store = store_with_inventory(:shampoo, 10)
    sut = Customer.new

    success = sut.purchase(store, :shampoo, 5)

    expect(success).to be true
    expect(store.inventory(:shampoo)).to eq 5
  end

  def store_with_inventory(product, quantity)
    Store.new.tap { |s| s.add_inventory(product, quantity) }
  end
end
```

- `let` はテストごとに評価し直されるので、実行時に状態が共有されるわけではない（2章の隔離の問題は起きない）。問題は**書き換えるときの結び付き**と**読みやすさ**
- FactoryBot の `create(:product, stock: 10)` のように、テストに効く値をその場で明示するのも同じ考え方
- 例外として、ほぼ全テストで同じになる基盤の準備（DB 接続など）は共通化してよい。RSpec なら `rails_helper` の設定や `shared_context`

### 疑問③：これは意識したことなかった。アンチ・パターンとして絶対覚える

前提がテストの外に隠れていて、テストを読んでも分からない状態には名前が付いている。『xUnit Test Patterns』の **Mystery Guest（謎の客）** という悪臭（test smell）。RSpec の世界でも、thoughtbot のブログ記事「Let's Not」などで `let` の多用は以前から指摘されている。

`let` の利点（重複が減る、遅延評価される）も本物なので、何を優先するかのトレードオフ。

| | `describe` 直下の `let` / `before` | `it` の中 + ファクトリ・メソッド |
| --- | --- | --- |
| 重複 | 少ない | 少し増える |
| テスト1つを読むとき | 上に戻って前提を探す | その場で完結する |
| 前提を1つ変えたとき | 他のテストに波及する | そのテストだけで済む |
| ネストが深くなったとき | `let` の上書きが重なって追いにくくなる | 影響なし |

落とし所は、テストの結果に効く値（在庫 10 と 15 のような）は各 `it` の中に書き、どのテストでも変わらないものだけを `let` にする。

### 疑問④：パラメータ化テストは、まとめすぎず正常系と異常系を分けるのがいい？

そう思う、で一致。`true` / `false` が並ぶと、どれが境界なのかを読み解く必要が出てくる。

```ruby
# 正常系と異常系を1つにまとめた形
[
  [-1, false],
  [0,  false],
  [1,  false],
  [2,  true],
].each do |days_from_now, expected|
  it "#{days_from_now}日後の配達日の妥当性は #{expected} である" do
    delivery = Delivery.new(date: Date.current + days_from_now)

    expect(DeliveryService.new.delivery_valid?(delivery)).to eq expected
  end
end
```

```ruby
# 正常系と異常系を分けた形（本の推奨）
[-1, 0, 1].each do |days_from_now|
  it "#{days_from_now}日後の配達日は不正である" do
    delivery = Delivery.new(date: Date.current + days_from_now)

    expect(DeliveryService.new.delivery_valid?(delivery)).to be false
  end
end

it "最短の配達日は2日後である" do
  delivery = Delivery.new(date: Date.current + 2)

  expect(DeliveryService.new.delivery_valid?(delivery)).to be true
end
```

- 入力を見ただけで何を検証しているか明らかなら、1つにまとめてよい
- そうでなければ分ける。振る舞いが複雑すぎるなら、パラメータ化せず1つずつ書く
- RSpec には xUnit の `[Theory]` のような標準機能は無いので、配列のループか rspec-parameterized gem の `where` を使う

日付をパラメータにするときは評価のタイミングに注意する。日付そのものを配列に入れるとファイルの読み込み時に評価され、`it` の中で `travel_to` しても固定されない。本と同じく、日数の差分だけを渡して日付は `it` の中で組み立てる。
