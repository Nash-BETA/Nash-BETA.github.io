# 16章：独立性 まとめ

## 要点

### ユースケース

- 良いアーキテクチャはコード構造から「何のシステムか」が読み取れる
- フレームワーク（Rails、Spring）が叫んではいけない。**ユースケースが叫ぶ**べき
- 「ドメイン × 動詞」（例：`services/orders/place_order.rb`）でユースケースを構造に表す
- ネームスペースを切るのもユースケースを叫ばせる手段の一つ

### 運用

- ユースケースが構造に現れていれば、運用者はディレクトリを見るだけで「どこを触ればどの機能が動くか」がわかる
- 15章「インフラ運用」とは別レイヤー。ここでは**コードの可読性・追跡性**が運用コストを下げる話

### 開発

- アーキテクチャは「チームが並行して開発を進められる形」になっているべき
- ユースケース・ドメインで分かれていれば、チームごとに担当領域を持って独立に作業できる
- **コンウェイの法則**：組織構造とアーキテクチャは鏡像になる

### デプロイ

- 良いアーキテクチャは、コンポーネント単位で独立にデプロイできる
- モノリスでも実現できる：境界が綺麗なら変更が局所化されてリリースコストが下がる
- 14章 SDP（安定依存の原則）が効く

### 選択肢を残しておく

- 「方針と詳細を分けて、詳細の決定を遅らせる」を独立性の文脈で押し直す節
- 注文ロジックを書く時点で、PostgreSQL / MySQL / Stripe / PAY.JP を**決めなくていい**状態が理想

### レイヤーの切り離し

- ソフトウェアを水平方向のレイヤーで切り離す
- UI / ユースケース / ビジネスルール / DB・FW
- 各レイヤーは異なる理由で変わる → 境界を引けば変更の影響を局所化できる
- 13章 CCP（共通閉鎖の原則）の応用

### ユースケースの切り離し

- レイヤーで横に切ったあと、さらに縦方向にユースケースで切り離す
- レイヤー（横）× ユースケース（縦）の**格子状**に切ることで、変更の影響範囲を最小化できる
- 「叫ばせる」と「変更を局所化する」は同じ手段で両方達成できる

### 切り離し方式

- ソースレベル / デプロイレベル / サービスレベル の3段階
- 軽い順：ディレクトリ分割 → Engine・packwerk → マイクロサービス
- どのレベルが正解かは状況による。最初は軽く始めて、必要になったら強くする

### 独立した開発が可能

- ユースケースで切り離されていれば、チームごとに担当領域を持って並行作業できる
- 切り離しレベル（ソース/デプロイ/サービス）が強いほど、チームの独立性も強くなる

### 独立デプロイ可能性

- コンポーネント単位で独立にデプロイできる
- 14章 SDP がここで効く：依存方向が安定側に向かっていれば、上流の変更が下流に波及しない
- 開発の独立とセット：開発が独立にできても、デプロイで全部巻き込むなら意味が半減

### 重複

- **本物の重複**（同時に変わる）：DRYで消すべき
- **偽物の重複**（別々に変わる）：消してはいけない。共通化すると両方の変更理由を引きずり込む怪物になる
- 判断基準：「**同時に変わるか？**」

### 切り離し方式（再び）

- 最初は弱い切り離し（ソースレベル）から始めろ
- 後から強くできる構造にしておけ
- 強くしすぎたら戻すのも大変
- 「**まずは軽く切れ。境界はちゃんと引け。重くするのは必要になったときだけ**」

### 結論

- 良いアーキテクチャは4つの独立性を支える：**ユースケース・運用・開発・デプロイ**
- レイヤーで横に切る、ユースケースで縦に切る、適切なレベルで切り離す、詳細の決定を遅らせる
- 同じ理由で変わるものはまとめ、違う理由で変わるものは分ける
- アーキテクトの仕事は「**未来の選択肢を可能な限り残す**」こと

## 疑問①：ユースケースが叫ぶ構造って具体的にどう書く？

Rails の規約は活かしつつ、ユースケースを叫ばせる：

```
app/
├── controllers/
│   ├── orders_controller.rb              # 注文機能がある
│   ├── refunds_controller.rb             # 返金機能がある
│   └── shipments_controller.rb           # 配送機能がある
│
├── services/                       # ユースケース層
│   ├── orders/
│   │   ├── place_order.rb          # 注文を受け付ける
│   │   ├── cancel_order.rb         # 注文キャンセル
│   │   └── apply_coupon.rb         # クーポン適用
│   ├── refunds/
│   │   └── issue_refund.rb         # 返金処理
│   └── shipments/
│       └── arrange_shipment.rb     # 配送手配
│
└── models/
    ├── order.rb
    ├── refund.rb
    └── shipment.rb
```

ポイント：

- Rails の規約（`controllers/` `models/` `services/`）は守ったまま
- **その下のディレクトリ名・ファイル名**で「何のシステムか」を叫ばせる
- `services/orders/place_order.rb` のように「ドメイン × 動詞」で書くとユースケースが構造から読める

**ネームスペースを切るのもユースケースを叫ばせる手段**であり、13章 CCP の「同じ理由で変わるものをまとめる」をファイル/ディレクトリ単位でやっていることに等しい。

## 疑問②：マイクロサービスやモジュラーモノリスはこの独立性の話から生まれた？

その通り。「独立性をどこまで物理的に担保するか」のグラデーション：

| 形態 | 独立性の担保レベル | コスト |
|-----|-----------------|------|
| ベタ Rails（層分け） | 弱い（コーディング規約頼み） | 安い |
| **モジュラーモノリス** | 中（packwerk 等で依存方向を強制） | 中 |
| **マイクロサービス** | 強い（ネットワーク越しで物理分離） | 高い |

Martin の主張は「論理的にユースケースで分けろ」という思想で、それを：

- **同じプロセス内で頑張る** → モジュラーモノリス
- **別プロセスに切り出す** → マイクロサービス

という選択肢が現代では生まれた、という流れ。ただし**いきなりマイクロサービスから入るな**というのが暗黙の主張。まず軽く切って、必要になったら段階的に強くする。

## 疑問③：「選択肢を残しておく」ってSDPの話？

近いけど、正確には**3つの原則が絡み合ってる**：

| 原則 | 「選択肢を残しておく」との関係 |
|-----|---------------------------|
| **DIP**（依存性逆転）| 一番直接的。詳細→方針に依存させることで詳細の差し替えを可能にする |
| **SAP**（安定抽象）| 安定なもの（=方針）は抽象的であるべき。だから詳細を直接書かない |
| **SDP**（安定依存）| 依存は安定側に向かう。詳細（不安定）→ 方針（安定）の方向 |

骨格は **DIP**：

```ruby
# DIPなし：選択肢を残せていない
class PlaceOrder
  def call(params)
    Stripe::Charge.create(...)   # Stripe決め打ち
  end
end

# DIPあり：選択肢を残せている
class PlaceOrder
  def initialize(payment_gateway:)
    @payment_gateway = payment_gateway
  end

  def call(params)
    @payment_gateway.charge(...)  # 中身は後で選べる
  end
end
```

DIP で構造を作って、SDP・SAP でその構造が健全かを検証する関係。

## 疑問④：「ユースケースの切り離し」と最初の「ユースケース」節は同じ話では？

正直に言うと**かなり重なる**。Martin の本自体が同じ主張を角度を変えて繰り返す書き方になっている。

無理に区別すると：

| 節 | 焦点 |
|---|------|
| **ユースケース**（最初の節）| 「叫ばせる」=構造から**何のシステムか読み取れる**状態（目的） |
| **ユースケースの切り離し**（後の節）| 「変更を局所化する」=**変更の影響範囲を最小化**する技法（手段） |

実装としてはほぼ同じことをやるので、現場で使い分ける意味はあまりない。**「同じ手段で2つの効能が得られる」**と理解しておけば十分。
