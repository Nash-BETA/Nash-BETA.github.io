# 17章：境界線：境界線を引く まとめ

## 要点

### 結合の悲しい物語

- 境界線を引かなかったプロジェクトの失敗談を通じて「**境界線を引かないと痛い目に遭うぞ**」と読者をビビらせる節
- 理屈ではなく体験談で恐怖を植え付けるのが目的
- DB・FW・UI を早期に決め込むと、後で取り返しがつかない
- 答えは出さず、痛みだけ植え付けて次の節に渡す Before パート

### FitNesse

- 結合の悲しい物語の具体例として独立して語られる成功事例（Martin 自身が関わった）
- 受け入れテストツール FitNesse の開発で、当初は「Web ベースなので DB が必要」と思い込まれていた
- Martin が「**DB は詳細**」と主張して境界線を引かせた → 永続化処理は抽象インターフェース越しにだけ呼ぶ
- 開発が進む中で「**実は DB 要らない、フラットファイルで十分**」と気づいた
- もし最初から MySQL ベタ書きしていたら、剥がすのに莫大な労力がかかった
- 「**DB を使うかどうか**」も詳細であり、決め込む前に境界線を引いておけ

### あなたの境界線は何か？いつ境界線を引くか？

- **何を**：「**変化の軸**」に沿って引く（別の理由で・別のタイミングで変わるもの同士の間）
- **いつ**：できるだけ遅く、ただし「**変わりそう**」のサインが出た瞬間
- 早すぎる → 使うかわからない柔軟性のための抽象化を量産（YAGNI違反）
- 遅すぎる → すでに結合してしまって剥がせない（結合の悲しい物語）
- 全部に引く必要はない。変化の軸が見えた箇所だけに引く

### 入力と出力はどうする？

- UI（入力と出力）は**ビジネスロジックの中心ではない**
- システムの核はビジネスルールで、UI はそこにデータを流し込む・流し出す**周辺**でしかない
- 同じユースケースを **Web・CLI・API・モバイル**から呼べる状態が理想
- Rails は MVC で View を中心に語られがちだが、Martin の視点では「View は最後の仕上げ」程度の位置づけ

### プラグインアーキテクチャ

- 境界線を引いた結果、システムは「**中心（ビジネスルール）+ 周辺（プラグイン）**」という構造になる
- IDE と拡張機能の関係：ホストはプラグインの詳細を知らない、プラグイン側がホストのインターフェースに合わせる
- DB / UI / 外部サービス / Web FW は全部「ビジネスルールに後付けされたプラグイン」として扱う
- 依存方向：**プラグイン（不安定）→ ビジネスルール（安定）**（DIP + SDP + SAP の最終形）

### プラグインの戦い

- プラグインアーキテクチャは「**依存方向の戦い**」だ、という主張
- 普通にコードを書くと依存は自然に双方向になりがち：
  - Rails の便利な機能を使いたい → ビジネスルールが ActiveRecord に依存
  - Stripe SDK が直接呼べると楽 → UseCase が `Stripe::Charge` をベタ書き
  - ライブラリの例外をそのまま rescue → ドメインに外部例外が漏れる
- 戦いの装備：
  - インターフェース（抽象）は**ホスト側が所有**する
  - **DI（依存性注入）**でプラグインを差し込む
  - **packwerk / rubocop** で依存方向を機械的に強制
  - **コードレビュー**で文化として守る
- 一度勝っても終わらない。**継続的な戦い**

### まとめ

- 境界線を引く目的：**詳細の決定を遅らせる / 変更を局所化 / テスト容易性**
- 引く場所：**変化の軸**
- 引くタイミング：早すぎず、遅すぎず
- 結果として現れる構造：**プラグインアーキテクチャ**
- 維持には継続的な戦いが必要
- 一言：**「境界線は引くものではなく、引き続けるもの」**

## 疑問①：「結合の悲しい物語」って何が言いたいの？

理屈ではなく**体験談で「境界線を引かないと痛い目に遭うぞ」と読者をビビらせるための節**。

3つの悲劇に共通する Martin のメッセージ：

1. **早すぎる決定は罪**：プロジェクト初日に「DB は MySQL」「Web は Spring」を決め込むと詰む
2. **混ぜたら戻れない**：ビジネスロジックに DB クエリや FW を直書きすると剥がせない
3. **正解は「決めない・混ぜない」**：詳細を後で決められるよう境界線で隔離しておく

具体策はこの節では出ない。**問題提起と痛みだけ植え付けて**、次の節（あなたの境界線は〜）で答えを出す構成。

| 節 | 役割 |
|---|------|
| 結合の悲しい物語 | **Before**：境界線がないとこうなる（恐怖） |
| FitNesse | **After**：境界線を引いていたら助かった（成功） |
| あなたの境界線は〜 | **解決**：じゃあどう引くか |
| プラグインアーキテクチャ | **How**：具体的な構造 |
| プラグインの戦い | **維持**：構造を守り続ける戦い |

## 疑問②：じゃあ、どこのタイミングで決定するのがいいの？

答え：**「できるだけ遅く、ただし判断材料が揃った時点で」**

### 判断材料のサイン

- **「ここ変わりそうだな」と感じた瞬間**（変化の軸が見えた瞬間）
- **候補が複数に絞られた**（Stripe / PAY.JP / Square など）
- **チーム・関心が分かれた**

### やっちゃいけないタイミング

- プロジェクト開始時に「DB は MySQL です」と決め込んでベタ書き
- まだ要件もブレてる段階で「マイクロサービスでいきます」
- 「将来○○するかも」レベルの妄想で境界線を量産

### 落とし所

「**DB を使う**」までは決めていいが、「**PostgreSQL か MySQL か**」は後で良い。これは Martin の主張とほぼ一致する（純粋クリーンアーキテクチャでは「DB を使う」自体も詳細扱いだが、中規模 Rails 現場の感覚としてはこのバランスで OK）。

```ruby
# 1. 最初はベタでOK
class PlaceOrder
  def call(params)
    Stripe::Charge.create(...)   # ベタ書きで動かす
  end
end

# 2. 「PAY.JP も試したい」が出てきた瞬間に境界線を引く
class PlaceOrder
  def initialize(payment_gateway:)
    @payment_gateway = payment_gateway   # ここで初めて抽象化
  end
end
```

つまり：必要になるまで境界線は引かない（YAGNI）。でも「変わりそう」と感じた瞬間に即引く（手遅れになる前に）。

## おまけ：Rails レイヤリング（境界線思考の応用）

ここからは厳密には17章の本筋ではなく、**16章の独立性 + 13章 CCP + Rails 文化**の応用議論。ただし「変化の軸に沿って境界線を引く」という17章の核となる思想は内部レイヤリングにも効く。

### Q1：Controller から Model のメソッドを直接呼ぶのは良くない？

ケースバイケース。「悪い」と言い切れない。

**OK**：単純CRUD・1モデル完結

```ruby
class UsersController < ApplicationController
  def show
    @user = User.find(params[:id])      # ✅ OK
  end

  def update
    @user = User.find(params[:id])
    @user.update!(user_params)          # ✅ OK
  end
end
```

**NG（Service に切り出すべき）**：複数モデル + 副作用がある業務フロー

| サイン | 説明 |
|------|------|
| 複数モデルを触る | Order + Inventory + Payment + Mailer など |
| トランザクションが必要 | 全部成功 or 全部ロールバック |
| 副作用がある | メール送信、外部API呼び出し |
| 同じロジックを別所からも呼びたい | API、Job、CLI からも使う |
| Controller が20行超える | 明らかに肥大化 |

### Q2：Model のメソッドで別テーブルを更新するのはダメ？

判断基準：**「そのテーブルは、この Model の『身体の一部』か？」**

- **OK**：has_many の子、自分のログ、自分のステータス履歴（同じドメイン内）
- **NG**：別ドメインのリソース（在庫、通知、決済など）

特に危険：**callback で他テーブルを触る**

```ruby
# ❌ 暗黙の副作用地獄
class Order < ApplicationRecord
  after_create :reserve_inventory
  after_update :notify_user
  after_destroy :issue_refund
end
```

→ `Order.create` するだけで全部走る。テストデータの組み立てが破綻する。

正しい書き方：**ドメイン跨ぎは Service が仕切る。Model はそれぞれ自分のドメインに閉じる**。

### Q3：同じドメイン内でも Service に切り出すべき？

ケースバイケース。2つの流派がある：

| 流派 | 特徴 |
|---|---|
| **Rails 流（Fat Model）** | 規約通り、シンプル、ファイル少ない |
| **Clean Architecture 流（Anemic Model + Service）** | 単一責任、テスト軽い、冗長 |

判断基準：

- 1〜3行で完結 / 副作用なし / 自己完結 → **Model でOK**
- 10行超え / トランザクション長い / 外部依存あり / 別所から呼ぶ → **Service に出す**

### 17章本筋との関係

| 軸の種類 | スケール |
|---------|---------|
| 17章本筋の境界線 | ビジネスルール ↔ 詳細（DB・UI・FW） |
| Rails レイヤリング | Controller / Service / Model（ビジネスルール内部） |

スケールは違うが、**「変化の軸を見つけて境界線を引く」という考え方は同じ**。なので17章の応用と言える。
