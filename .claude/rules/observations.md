# 対話ログからの気づきメモ

壁打ちセッション中の気づきを記録する。レトロスペクティブ時に参照してsparring.mdに反映する。

## 記録例

```
## YYYY-MM-DD ◯章

### うまくいった
- 〜のときに〜した。ユーザーの反応：〜

### うまくいかなかった
- 〜してしまった。ユーザーの指摘：〜。学び：〜
```

---

## 2026-04-16 第三部SOLID・第四部12-14章

### うまくいった

- 自分の実装コード（BaseService）を題材にしたらエンジン全開になった
- 「本の主張」と「現実のトレードオフ」を対比する説明（OCPの「変更ゼロは無理」など）
- 悪い例→良い例の順でコードを示す
- ユーザーの疑問をまず肯定してから補足・訂正する
- 1回の返答で1〜2ポイントに絞る

### うまくいかなかった

- 最初のOCPまとめでユーザー自身の指摘が反映されていなかった → 「自分の話が反映されていない」と指摘された。学び：まとめはユーザーが実際に言ったことを軸にする
- コンポーネントの説明で「デプロイできる単位」と言ったら違和感を持たれた → 用語の定義を曖昧にしない。デプロイとリリースの違いなど、言葉の境界を揃える
- 「Recordだけ切り出しても意味がない」と言い切った → ユーザーに「リリースを小さくするなら分けてもいい」と指摘され訂正。学び：言い切り型の主張をする前に、トレードオフを確認する

### 観察

- ユーザーは「それってメタプロ？」のような類似概念との比較質問が多い。SOLIDや設計原則は「似てるけど別物」の対比で説明すると腑に落ちやすい
- 用語の違和感にこだわるタイプ。「デプロイとリリースの違いは？」のような質問が出る
- 「ok」「次」で切り上げを示す。詰め込みすぎを嫌う

## 2026-04-21〜23 第五部15章

### うまくいった

- 「洞窟探索って仕様調査のこと？」にドキュメント系（仕様調査）とコード系（洞窟探索）を明確に切り分けて答えた。ユーザーの反応：「okok、ありがとう」
- 「運用の話はコードの話？インフラの話？」という違和感に対し、Martinの本が2つのレベル（インフラ運用とコード運用）を混ぜていると認めて整理した。ユーザーの反応：「言われた通りですわ」
- ユーザーからの言い換え指示（例：「殴れば→追加すれば」「探索コスト→洞窟探索」）に素直に従い、反論や補足を挟まなかった
- 要点と別セクション（ポイント）が重複していたとき、指摘を受けて素直に削った

### うまくいかなかった

- 要点提示のあと、選択肢A〜Dを並べてユーザーに選ばせる形式で質問を連投した → ユーザーに「やり方が変わった、要約を出して自分が質問するスタイルだったのでは」と指摘された。学び：壁打ちの主導権はユーザー側。こちらは要約を提示し、ユーザーの疑問を待つのが基本形。質問は「普段どうしてますか」程度の現場引き出しに留め、選択肢で答えさせるような質問攻めにしない
- 参照している版を聞かれた際、特定の版に基づいていないことを伝える必要があった。学び：意訳であることを最初から明示しておくと、用語の違和感で時間を取らずに済む（今回は序盤で確認できたのでギリギリOK）
- まとめの見出しに「要点」と「ポイント」を並置したら内容が重複していた。学び：見出しは重複しないように役割を分ける。まずは箇条書き一本で出して、必要になったら分割する

### 観察

- ユーザーは見出しごとに進めるスタイルを好む。「1つずつ要点を出してもらい、それに自分が質問する」形式
- まとめの文言について細かく言い換え指示が入る（「殴れば→追加すれば」「探索コスト→洞窟探索」など）。ユーザー自身の言葉に寄せるのが重要で、こちらが意訳したまま押し通さない
- 「具体的に教えて」の問いに対しては、Railsの悪い例→良い例の対比で示すと刺さる

## 2026-04-28 第五部15章（残りセクション）

- 「ようはどういうことだってばよ」に対して、3つの例を1つの表に整理してRailsアナロジー（Mysql2直叩き vs ActiveRecord）で答えた → ユーザーの反応：「おk。」で受容された

- 残りセクションを「ダイレクトメール / 物理アドレス指定 / 結論」と最初に提示してから1つずつ進めた

### 観察

### うまくいかなかった

- 17章の節構成（特に「結合の悲しい物語」と「FitNesse」が別節であること、「プラグインの戦い」「まとめ」の存在）が記憶ベースでズレていた。学び：構成不確実な章では最初に目次を聞く、または序盤で「自分の記憶では...」と前置きして共有しておく

### 観察

- ユーザーは「で、何が言いたいの？」と章構成や節の意図を問う質問が出る。これに対して「この節は何のために配置されているか」を構成上の役割で答えると刺さる
- Rails の実務質問が連続するとき、本筋から離れることがある。離れたこと自体は問題ないが、まとめでは本筋と派生を分ける扱いが受け入れられた
- 「ケースバイケース」で答えるとき、トレードオフ表 + 判断基準 + 具体例の3点セットで提示すると納得感が出る
- ユーザーは原理主義的な答え（Martin の理想）と現場の落とし所（Rails 文化）の両方を求めている。一方だけだと物足りない
